# Fitician–TetraPay API v1

Release candidate only. No production deployment or paid transaction is authorized.
Credentials are supplied later through the Iran server environment, never source code.

## Architecture and files

The existing billing system remains the source of truth. `BillingOrder` owns the
price/currency/package snapshots. Its `BillingTransaction` owns the immutable
external `order_id` (transaction UUID), provider token, environment, hosted URL,
and durable retry schedule. The existing provider/token unique constraint prevents
allocating one token twice. Existing `fulfill_paid_order` and grant idempotency
produce one subscription per order.

- `backend/app/billing/providers/tetrapay.py`: v1 adapter, exact amount checks, raw-body signatures.
- `backend/app/billing/{service,reconciliation,router,repository,models}.py`: checkout reuse, locks, returns, webhooks, scheduler recovery.
- `backend/app/config.py`, `backend/app/scheduler/worker.py`: validated settings and Iran scheduler loop.
- `backend/alembic/versions/20261123_176_tetrapay_recovery.py`: additive nullable recovery fields, attempt count and index. Historical records remain intact.
- `packages/fitician-core/src/billing.ts`: provider contract, available methods and URL validation.
- `frontend/src/features/billing/`: existing checkout, result and API; plans use server offer availability.
- `frontend/nginx.conf`: query/referrer-free access logs and no-store/no-referrer payment returns.
- `frontend/src/features/auth/ProtectedRoute.tsx`: retain return query through authentication.
- `mobile/billing/`, `mobile/entitlements/EntitlementProvider.tsx`, `mobile/config/runtimeConfig.ts`, `mobile/app.config.ts`: durable purchase identity, startup/resume verification and distribution gate.
- `.env.example`, `ops/env/iran.env.example`, `compose.prod.iran.yaml`: disabled examples and existing env-file injection.
- `contracts/openapi.json`, `packages/fitician-core/src/generated/api.ts`: regenerated Fitician API contract.
- Backend billing/database tests, web billing tests, mobile billing/config/native entitlement tests and shared billing contract tests cover this integration.

## Official contract

Retrieved 2026-11-23 from [API documentation](https://tetra98.com/docs) and
[developers](https://tetra98.com/developers). `tetrapay-openapi.json` is the complete
OpenAPI 3.1.1 export generated by the official documentation's download function,
including schemas, errors, examples and webhook headers. The documentation generates
the export in JavaScript rather than linking a static specification URL.

Production base: `https://api.tetra98.com/api/v1`.
Sandbox base: `https://api.sandbox.tetra98.com/api/v1`.
Authentication: server-only `Authorization: Bearer <api_key>`.

| Operation | Use |
| --- | --- |
| `POST /payments` | Create or recover an invoice using the same transaction UUID and amount |
| `GET /payments/{token}` | Documented read-only status; never sufficient for fulfillment; adapter uses verify instead |
| `POST /payments/{token}/verify` | Authenticated, repeatable definitive verification; no request body |
| `POST /payments/{token}/partial/{decision}` | Documented accept/reject; intentionally never called by Fitician |
| `POST <webhook_url>` | Optional signed definitive payment event |

The legacy `/api/create_order` and `/api/verify` are not used. No refund endpoint
appears in the current specification; automated refunds are explicitly unsupported.

| `TETRAPAY_CALLBACK_URL` | `https://fitician.fit/billing/checkout-result` |
| `TETRAPAY_WEBHOOK_ENABLED` | `false`; optional; enabling requires separate nonblank signing key |
| `TETRAPAY_WEBHOOK_SECRET` | Separate `SecretStr`; never substituted with the API key |

Callback/webhook paths are fixed; HTTPS Fitician subdomains are permitted for
isolated nonproduction sandbox hosts. Production requires `fitician.fit` itself.
No credentials are needed for disabled startup or mocked tests. Invalid explicitly
enabled configuration fails startup rather than offering an unusable gateway.
`GET /api/v1/billing/checkout-methods` exposes only enabled provider names/default.
Offers become unavailable when no provider is registered.

## Creation and verification

1. An authenticated customer creates/reuses an order with an idempotency key. Prices come from the server catalog.
2. Checkout locks the order and reuses its open transaction. The transaction UUID is committed before the HTTP request.
3. TetraPay receives a numeric string in IRR, the transaction UUID, validated callback and `allow_partial=false`. No customer phone/email is sent.
4. The official provider URL and token are persisted before returning. Clients validate HTTPS and official TetraPay domains before opening.
5. Repeating creation after a timeout uses exactly the same UUID and amount. This is permitted by TetraPay's documented same-`order_id` idempotency contract (200 reuse, 409 amount conflict). No immediate transport retries are made.
6. Return parameters `token` and `status` are untrusted. An authenticated POST to `/api/v1/billing/tetrapay/return` maps the token to that user's persisted transaction and verifies through TetraPay. Other users receive no payment details.
7. Legacy transaction/order result routes continue working. Login retains query parameters; refresh and repeated verification are safe.
8. Only a conclusive verified full payment calls existing fulfillment and refreshes client entitlements. Pending/created/cancelled checkout attempts remain recoverable: TetraPay cancellation/failure returns `created`, not a definitive failure.

All amounts use integers. TetraPay's currency is IRR by contract (there is no
currency field in its response). Verify compares invoice `amount` with the stored
IRR snapshot, `payable_amount = amount + fee_payer`, and requires
`received_amount >= payable_amount`. It also validates fee totals and
`net_amount = amount - fee_merchant`. Merchant net proceeds need not equal the
invoice. No commission percentage is hardcoded. Provider-managed commission policy
remains authoritative. Accepted partial payments are rejected even when `status=paid`.

## Webhook setup and races

Generate a `whsec_...` key in gateway Settings; it is shown once. Register the
HTTPS webhook URL there and provision that separate key on the server. Each newly
created payment also supplies `webhook_url` when webhooks are enabled. TetraPay
freezes the webhook destination at link creation, so changing dashboard settings
will not move existing payments' callbacks. Key rotation applies to retries too.

Fitician authenticates `X-TetraPay-Signature: t=<unix>,v1=<hex>` with HMAC-SHA256
using the literal signing key on `timestamp + '.' + exact raw body`, constant-time
comparison and a ±300 second timestamp window. Keep server time synchronized.
JSON bodies are bounded to 64 KiB. Event/type/ID headers must match the signed
body. Sandbox header/body must match the provider environment. Tokens, transaction
UUIDs, snapshots and full obligation are checked before applying any result.

`payment.paid` and `payment.underpaid` use the same reconciliation function as
customer verification. Order row locks serialize replicas, followed by fresh
transaction reads; grant idempotency and provider-token uniqueness are durable.
Event IDs are validated but not stored in a separate inbox: duplicate deliveries
are harmless because the persisted payment/fulfillment state is the idempotency
boundary. Late pending events cannot regress verified/refunded payments. A webhook
racing an unpersisted provider token receives 503 so TetraPay retries.

No key or disabled flag means HTTP 503, never signature bypass. Checkout and the
scheduler work without webhooks. A dashboard-level webhook may still be delivered
when disabled locally; it is rejected. Successful deliveries return 200. TetraPay
retries failures after 1, 2, 5, 10, 30, 60, 120 and 240 minutes (nine attempts total).
Only local DB processing occurs in the webhook; there is no external HTTP wait.

## Recovery, late payments and operations

The existing Iran scheduler processes at most five due transactions per minute.
Retries survive restarts in PostgreSQL, start at 60 seconds and back off to six
hours, with at most 64 automatic attempts per transaction. Numeric `Retry-After`
is respected (up to a day), with the documented `error.retryAfter` fallback.
An indexed deadline in sanitized transaction evidence coordinates the cooldown
across invoices and replicas, including checkout creation; signed webhook processing
continues during the provider cooldown. User verification observes the same transaction's
backoff after the first check. API writes have no automatic HTTP retry. Lost
creation responses are recovered using documented creation idempotency. No access
is granted on timeouts, malformed responses or provider errors.

Separate scheduler replicas use `FOR UPDATE SKIP LOCKED`; customer/webhook paths
lock the same order before applying state. Verified/refunded transactions stop
polling. Expired links remain eligible for bounded late confirmation. After the
retry budget, retain the record for investigation; an authenticated customer can
explicitly retry verification. Do not delete unresolved payments. Review exhausted
transactions in admin billing and arrange owner/customer follow-up. An unmatched
or deleted-user payment requires manual investigation; never allocate it to another account.

**Late-payment policy:** honor any full authenticated provider-confirmed invoice,
even after Fitician's internal order TTL, with the original price/package snapshot.
Access begins at fulfillment under existing entitlement extension rules. Never
silently discard confirmed money or create a replacement invoice automatically.

Sanitized status, exact amount/commission strings, method and rejection reason are persisted
in `provider_evidence` and shown in the existing admin order detail. Tokens, personal
fields, credentials and raw payloads are excluded from this evidence.

Diagnostics use fixed payment event codes and the existing log bridge; no card
information, API credentials, signatures or raw payment bodies are emitted. Existing
admin billing history remains available. Treat provider references and hosted links
as restricted billing data. Do not send them or raw payloads to AI debugging tools.

## Refunds and underpayments

The refund adapter always reports unsupported; it cannot falsely acknowledge a
refund or revoke access from an unverified claim. Owners must arrange refunds with
TetraPay support/dashboard outside Fitician, retain the gateway record, and handle
any access adjustment through existing authorized admin tools with an audit trail.
No partial acceptance/rejection operation is implemented. Underpayment needs owner
policy/authority and provider investigation. Never grant full access manually just
because the dashboard says paid; verify the full payable amount and commissions.

## Mobile distribution

Web is independent. Android direct distribution can explicitly opt in with build
environment `FITICIAN_EXTERNAL_BILLING_ENABLED=true` and
`FITICIAN_DISTRIBUTION_CHANNEL=direct`. Defaults are closed. EAS `production` forces
store/disabled; iOS is always closed to external checkout in this implementation.
For internal Android sandbox testing use a dedicated nonstore build and isolated
sandbox backend. Review any regional store's own rules before release there; no
Myket/Bazaar exception is assumed. Google Play/App Store require a separate approved
billing implementation or an applicable enrolled storefront program; do not relabel
a store build as direct to bypass this gate.

References checked 2026-11-23: [Google Play Payments policy](https://support.google.com/googleplay/android-developer/answer/9858738),
[Apple review guidelines, 3.1](https://developer.apple.com/app-store/review/guidelines/).
These policies can change and are not evidence of Fitician enrollment/approval.

Native purchase identities are saved in SecureStore per user/offer before order
creation. Backend pending sessions survive app termination. Global entitlement
startup/resume recovery verifies up to three pending sessions, with a 30-second
resume throttle. Plans refresh after verified purchase. No mobile secrets or success
claims are trusted. Web callback remains usable without requiring a deep link.

## Deployment and rollback

1. Require explicit production deployment approval; do not merge or auto-deploy this branch.
2. Review the exact release SHA and current Iran Compose/env contract. Preserve unrelated regional work. No Germany change is needed.
3. Provision credentials only in `/opt/fitician-iran/.env`; preserve all existing secrets. Restrict the file to the deployment operator. Use the owner checklist below.
4. Run the established backup plus isolated restore/migration rehearsal. Migration `20261123_176` is additive. Older images tolerate extra columns, but a backend predating the `tetrapay` enum cannot read TetraPay billing rows. Record a TetraPay-compatible fallback image before activation.
5. Use the existing reviewed **full Iran** release workflow with explicit schema-migration approval (`ALLOW_SCHEMA_MIGRATIONS=true`). Backend-only rollout rejects schema changes. Follow `ops/deploy-regional.sh`'s existing approval, full-SHA, artifact and rollback checks; do not bypass them.
6. Release both APIs, scheduler and web together, initially with TetraPay disabled. All already receive `FITICIAN_ENV_FILE` through `env_file`; backend-2 inherits backend. Never edit IPs, SSH, DNS, database credentials or Germany Agent config for this integration.
7. Check migrations, readiness, both replicas, scheduler heartbeat, enabled-method response, admin history, and approved nonproduction sandbox evidence. Restart/recreate APIs and scheduler through the approved regional release mechanism after changing env values; a plain process restart may retain old container env.
8. Only after owner approval enable live settings and perform a separately authorized small live payment. Verify exactly one grant, mobile/web access, history and logs. Automated tests must never call live endpoints.
9. If checkout malfunctions, first stop new sales through admin offer availability while retaining TetraPay-enabled verification, callbacks and scheduler for existing payments. Do not strand customers by immediately discarding credentials.
10. Once pending payments are reconciled, disable TetraPay/webhooks in env and apply an approved rollout while retaining a backend that understands `tetrapay` history. This feature rollback requires no source edits. Before any TetraPay rows exist, an approved prior binary may be used; after activation, never roll the API back to a pre-TetraPay enum. A full binary rollback requires a previously reviewed TetraPay-compatible fallback image and worker recovery plan. Use existing regional rollback procedures only with compatible tags. Keep the additive schema and all billing rows; never downgrade, delete or rewrite payment history to make an old image load. Restore backups only under separately approved recovery procedures.

See [owner activation checklist](tetrapay-owner-activation.md).
